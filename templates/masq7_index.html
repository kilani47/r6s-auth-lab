Stage 1

No Rate Limit

POST /masquerade/op7/api/verify-otp
The code is only {{ otp_digits }} digits — 10,000 possibilities — and the verify endpoint has no rate limit and no lockout. Every wrong guess just comes back "invalid" and lets you try again. Loop 0000–9999 against it and one of them is the real code. A second factor with no throttling is a short password in disguise.
for i in $(seq -w 0 9999); do
  curl -s -X POST .../api/verify-otp -d "otp=$i" -b cookies.txt | grep -q '"ok": true' && echo "CODE: $i"
done

Stage 2

Forced Browsing

GET /masquerade/op7/roster/export
Don't attack the code at all — walk around it. The duty-roster export endpoint checks that you cleared the password step and forgets to check the OTP step. Once you've signed in (step 1), request it directly and the second gate simply isn't there. This is the most important lesson here: a 2FA check is worthless if the server only enforces it on the pages that remember to ask.

Stage 3

Weak Recovery

POST /masquerade/op7/api/recover
"Lost the duty phone? Use a backup code." Backup codes look like KAFE-0000 … KAFE-9999 — a tiny space, no rate limit, and any valid one skips the OTP entirely. The recovery path exists to bypass the second factor by design, so if it's weaker than the factor, the factor's strength never mattered. 2FA is only as strong as its weakest fallback.
